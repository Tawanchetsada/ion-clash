# บันทึกข้อตัดสินใจ (Decision Log)

ทุกข้อในนี้ตกลงกันแล้วก่อนเริ่มเขียนโค้ด หากจะเปลี่ยน ให้แก้ที่ไฟล์นี้ก่อนเสมอ
เหตุผลสำคัญพอ ๆ กับตัวคำตอบ เพราะอีก 3 เดือนจะจำไม่ได้ว่าทำไมถึงเลือกทางนี้

---

## D-01 · ข้อมูลสมการ 50 ด่าน — ผู้พัฒนาร่าง อาจารย์ตรวจ

**เลือก:** สร้างสมการทั้ง 50 ด่านจากกฎการละลายมาตรฐาน แล้วส่งตารางให้อาจารย์ที่ปรึกษาเซ็นรับรองก่อนใช้จริง

**เหตุผล:** โปรเจกต์ไม่มีชุดสมการที่ตรวจแล้วมาให้เลย ถ้ารอจะไม่ได้เริ่ม แต่ spec ห้ามเดาสมการโดยไม่มีผู้เชี่ยวชาญรับรอง ทางออกคือแยกสองขั้น — ร่างด้วยกฎการละลายที่ตรวจสอบได้ แล้วให้ผู้เชี่ยวชาญอนุมัติ

**ผลต่อการทำงาน:** Phase 2 ต้องผลิต `docs/chemistry-review.md` เป็นตารางให้อาจารย์เซ็น ก่อนที่ Phase 10 จะปิดได้

---

## D-02 · ขอบเขตไอออน — เพิ่มนอกสำรับการ์ดได้

**เลือก:** ใช้ไอออนจากสำรับการ์ด 10×10 เป็นแกน แต่เพิ่ม Pb²⁺, Ba²⁺, I⁻, Br⁻, S²⁻ ได้ และ **ตัด O²⁻ กับ MnO₄²⁻ ออก**

**เหตุผล:**
- `O²⁻(aq)` ผิดหลักเคมี — ออกไซด์ไอออนอยู่ในน้ำไม่ได้ มันไฮโดรไลซ์เป็น OH⁻ ทันที จึงตกตะกอนเป็น Al₂O₃ จากสารละลายไม่ได้
- `MnO₄²⁻` (แมงกาเนต) ไม่อยู่ในหลักสูตร ม.4 และไม่เสถียร ตัวที่นักเรียนเจอคือ MnO₄⁻
- Pb²⁺/I⁻ เปิดทาง PbI₂ ซึ่งเป็นตะกอนสีเหลืองสวยและเป็นตัวอย่างใน UI PDF หน้า 8 อยู่แล้ว
- Ba²⁺/SO₄²⁻ ให้ BaSO₄ ซึ่งเป็นตะกอนคลาสสิกที่สุดในหลักสูตร

**ผลต่อการทำงาน:** สำรับการ์ดกายภาพกับเว็บจะไม่ตรงกัน 100% ต้องแจ้งในเอกสารส่งมอบ

## D-03 · กลไกขั้น "ไอออน 4 → 4" — จับคู่ใหม่ + การ์ด 4 ใบเสมอ

**เลือก:** ช่องผลิตภัณฑ์ 4 ช่อง = **2 คู่** ผู้เล่นต้องแลกคู่ไอออนให้ถูก และแสดงการ์ด 4 ใบเสมอทุกด่าน โดยใช้ช่องกรอกสัมประสิทธิ์หน้าการ์ดบอกจำนวน

```
ก่อน:  [Na⁺] [Cl⁻] [Ag⁺] [NO₃⁻]
หลัง:  [Ag⁺][Cl⁻]  +  [Na⁺][NO₃⁻]
       └─ คู่ 1 ─┘     └─ คู่ 2 ─┘
```

**เหตุผล:**
- spec ระบุเงื่อนไขออกของ `arrangeProductIons` ว่า "ช่องครบ**และคู่ผลิตภัณฑ์ถูก**" — คำว่า *คู่* ยืนยันว่าต้องจับคู่ ไม่ใช่แค่ลากข้ามฝั่ง
- ถ้าแสดงไอออนซ้ำจริงตามจำนวน ด่านอย่าง `Al₂(SO₄)₃ + 3BaCl₂` จะมีการ์ด 12 ใบ ซึ่งพังบนมือถือแน่นอน
- การ์ด 4 ใบ + สัมประสิทธิ์ ตรงกับ UI PDF ทั้งหน้า 7 และหน้า 8 พอดี

**กติกาย่อย:**
- บังคับ **cation ก่อน anion** ภายในคู่ (ฝึกธรรมเนียมการเขียนสูตร)
- **ไม่บังคับ**ว่าคู่ตะกอนต้องอยู่คู่ที่ 1 หรือ 2 — สลับได้ทั้งสองแบบถือว่าถูก

**ผลต่อการทำงาน:** ขั้นตัดไอออนผู้ชมตัดการ์ดทั้งใบ (เช่น `2NO₃⁻` ตัดครั้งเดียว) ถูกต้องเพราะในปฏิกิริยาแลกคู่ที่ดุลแล้ว ไอออนผู้ชมมีจำนวนเท่ากันสองข้างเสมอ

## D-04 · ขั้นวางไอออนกับขั้นดุล — sub-step ในหน้าเดียว

**เลือก:** หน้า 2 มี 2 ช่วง — วางไอออนให้ครบก่อน แล้วช่องสัมประสิทธิ์จึงปรากฏ (เฉพาะด่านที่ต้องดุล) progress bar ยังแสดง 5 ขั้นตาม UI

**เหตุผล:** state machine ใน spec แยก `arrangeProductIons` กับ `balanceEquation` แต่ UI มีแค่ 5 หน้า ทั้งคู่จึงต้องอยู่หน้าเดียวกัน การซ่อนช่องสัมประสิทธิ์ไว้ก่อนช่วยลดภาระทางปัญญา (cognitive load) ของนักเรียน

## D-05 · ระบบคำใบ้ — 3 ระดับ ไล่จากกว้างไปแคบ ไม่เฉลย

**เลือก:** ปุ่มคำใบ้กดได้สูงสุด 3 ครั้งต่อด่าน หัก 10 คะแนนต่อครั้ง (สูงสุด 30 ตาม spec)

| ระดับ | เนื้อหา | ตัวอย่าง |
|---|---|---|
| 1 | ชี้หลักการ | "ปฏิกิริยานี้เกิดจากการแลกคู่ระหว่างไอออนบวกกับไอออนลบจากคนละสาร" |
| 2 | ชี้ไอออนที่ควรสนใจ | "ลองพิจารณาว่าไอออนเงินจับกับอะไรแล้วไม่ละลายน้ำ" |
| 3 | ชี้กฎการละลายที่เกี่ยวข้อง | "กฎ: เกลือคลอไรด์ละลายน้ำ ยกเว้นเมื่อจับกับ Ag⁺, Pb²⁺" |

**เหตุผล:** spec ห้ามเฉลยผลิตภัณฑ์ก่อนผู้เล่นผ่านการตรวจ คำใบ้จึงต้องพาคิด ไม่ใช่บอกคำตอบ การไล่ระดับทำให้นักเรียนที่ติดนิดเดียวไม่ต้องเสีย 30 คะแนน

**ผลต่อการทำงาน:** ต้องเขียนคำใบ้ 50 ด่าน × 3 ระดับ = 150 ข้อ (Phase 8)

## D-06 · เก็บข้อมูลวิจัย — ทำทั้ง local export และ Google Sheet

**เลือก:** ออกแบบเป็น `ResearchSink` interface แล้วทำสองตัว

1. **`LocalSink`** — เก็บ event log ใน localStorage มีปุ่ม "คัดลอกผลการเรียน" (คลิปบอร์ด) และ "ดาวน์โหลด CSV"
2. **`RemoteSink`** — ยิง POST ไป Google Apps Script Web App ที่เขียนลง Google Sheet อัตโนมัติ พร้อมคิวลองใหม่เมื่อเน็ตหลุด

**เหตุผล:**
- ไม่มี database และ deploy บน Vercel อย่างเดียว แต่ข้อมูลทั้งงานวิจัยเล็กมาก (8 คน × 50 ด่าน ≈ ไม่กี่ร้อย KB) จึงไม่จำเป็นต้องมี database จริง
- ทำสองทางเพราะวันทดลองจริงพลาดไม่ได้ — ถ้าเน็ตล่มหรือ Apps Script พัง ยังมีไฟล์ในเครื่องนักเรียนเป็นตัวสำรอง
- ปุ่ม**คัดลอก**สำคัญกว่าดาวน์โหลด เพราะบน iPad การหาไฟล์ที่ดาวน์โหลดแล้วเพื่อส่งต่อนั้นยากมาก แต่คัดลอกแล้ววางลง Google Form จบใน 5 วินาที

**ข้อควรระวัง:** `RemoteSink` ส่งข้อมูลออกเครือข่ายจริง ซึ่ง spec เดิมห้ามไว้ จึงต้องมีหน้าขอความยินยอมก่อนเริ่ม และเก็บเฉพาะรหัสผู้เรียน (S01–S08) ไม่เก็บชื่อจริง

## D-07 · E2 ทำบนกระดาษ เว็บคำนวณ E1

**เลือก:** เว็บเก็บและคำนวณเฉพาะ **E1** (คะแนนระหว่างเรียนจาก 50 ด่าน) ส่วน **E2** ผู้วิจัยกรอกคะแนนจากแบบทดสอบกระดาษเข้าหน้า `/research` เอง แล้วระบบคำนวณ E1/E2 คู่กันให้

**เหตุผล:** ลดขอบเขตเว็บลงมาก โดยไม่เสียความสามารถในการรายงานผลวิจัย

**สูตรที่ใช้ (ต้องให้อาจารย์ยืนยัน):**
```
E1 = (Σ คะแนนระหว่างเรียนของผู้เรียนทุกคน / N) / คะแนนเต็มระหว่างเรียน × 100
E2 = (Σ คะแนนหลังเรียนของผู้เรียนทุกคน / N) / คะแนนเต็มหลังเรียน × 100
เกณฑ์ 80/80
```

## D-12 · E1 ใช้คะแนนเกม 0-100 ที่หักแล้ว

**เลือก:** คะแนนระหว่างเรียนของ E1 คือคะแนนเกม 0-100 ที่หักคำใบ้และการตอบผิดแล้ว (ทางเลือก ก ใน Q-01)

**เหตุผล:** สะท้อนกระบวนการเรียนรู้จริง ผู้เรียนที่เข้าใจตั้งแต่แรกได้คะแนนสูงกว่าผู้ที่ต้องลองผิดลองถูก ซึ่งตรงกับความหมายของ "ประสิทธิภาพของกระบวนการ"

**ผลต่อการทำงาน:** `ResearchEvent.score` คือตัวเลขที่ใช้คำนวณ E1 โดยตรง แต่ยังเก็บ `wrongAttempts` `hintsUsed` และ `errorsByCode` ไว้ครบ เผื่ออาจารย์เปลี่ยนใจภายหลังจะได้คำนวณแบบอื่นย้อนหลังได้

## D-13 · คิด E1 รายด่าน สะสมไปเรื่อย ๆ ไม่ต้องรอครบ 50

**เลือก:** E1 คำนวณจากด่านที่ผู้เรียนเล่นจริง ไม่บังคับว่าต้องครบ 50

```
E1 ของผู้เรียนคนหนึ่ง = ผลรวมคะแนนของด่านที่เล่นจบ / (จำนวนด่านที่เล่นจบ x 100) x 100
E1 รวม = ค่าเฉลี่ยของ E1 รายคน
```

**เหตุผล:** 50 ด่านใช้เวลาราว 100 นาที ซึ่งอาจเกินคาบเดียว การคิดรายด่านทำให้เก็บข้อมูลได้ทันทีที่จบแต่ละด่าน ไม่ต้องรอให้ครบ และไม่เสียข้อมูลถ้าหมดเวลากลางคัน

**ผลต่อการทำงาน:**
- ยิงข้อมูลวิจัยทุกครั้งที่จบด่าน ไม่ใช่ตอนจบทั้งหมด
- หน้า `/research` ต้องแสดงจำนวนด่านที่แต่ละคนเล่นจบ ควบคู่กับ E1 เพื่อให้อ่านผลได้ถูกต้อง
- ต้องระบุในเล่มวิทยานิพนธ์ว่าผู้เรียนแต่ละคนเล่นกี่ด่าน

---

## D-14 · กรอกชื่อผู้เล่นก่อนเริ่มเกม เก็บใน game save

**เลือก:** เพิ่มหน้ากรอกชื่อผู้เล่นก่อนเริ่ม เก็บใน `GameSaveV1.playerName` และแนบไปกับข้อมูลวิจัยทุก event

**เหตุผล:** ผู้วิจัยต้องแยกได้ว่าข้อมูลชุดไหนเป็นของใคร โดยเฉพาะเมื่อคิด E1 รายคนตาม D-13

**ข้อควรระวังที่ต้องแจ้ง:** spec เดิมเขียนว่า "ไม่เก็บชื่อ โรงเรียน อีเมล หรือข้อมูลส่วนบุคคลใน MVP" การเก็บชื่อจึงเป็นการเปลี่ยนแปลงจาก spec ที่ต้องทำสองอย่างควบคู่

1. หน้าขอความยินยอมต้องระบุชัดว่า**เก็บชื่อผู้เล่น**และส่งขึ้น Google Sheet
2. แนะนำให้ใช้ชื่อเล่นหรือรหัสนิสิตแทนชื่อจริงเต็ม และเขียนคำแนะนำนี้ไว้ใต้ช่องกรอก

**ผลต่อการทำงาน:** เพิ่มฟิลด์ใน save schema · เพิ่มหน้ากรอกชื่อ · แก้ข้อความความยินยอม · แก้ `docs/assumptions.md` ให้ระบุว่าต่างจาก spec ข้อนี้

## D-15 · สารที่ละลายน้อย เก็บไว้ ยกเว้น CuCO3

**เลือก:** คงไว้ทั้ง PbCl2 · PbSO4 · MgCO3 · Fe(OH)2 แต่ **ตัด CuCO3 ออก** และเปลี่ยนด่าน 39 เป็น `2AgNO3 + Na2S -> Ag2S + 2NaNO3`

**เหตุผล:**
- PbCl2 PbSO4 MgCO3 เป็นตะกอนตามกฎการละลายมาตรฐานที่สอนในระดับ ม.4 ตำราไทยจัดเป็นไม่ละลายทั้งหมด
- Fe(OH)2 ถูกออกซิไดซ์ในอากาศได้จริง แต่ ณ ขณะเกิดปฏิกิริยาคือ Fe(OH)2 ถูกต้อง และเป็นตัวอย่างมาตรฐานที่ใช้เทียบกับ Fe(OH)3
- **CuCO3 ต่างออกไป** เพราะในความเป็นจริงไม่ได้ CuCO3 บริสุทธิ์ แต่ได้ copper(II) carbonate hydroxide ซึ่งเป็นความผิดพลาดทางเคมีจริง ไม่ใช่แค่เรื่องเส้นแบ่งการละลาย
- Ag2S ที่ใช้แทนเป็นตะกอนสีดำที่ไม่ละลายอย่างชัดเจน ไม่มีข้อโต้แย้ง และให้อัตราส่วน 2:1:1:2 ซึ่งเป็นรูปแบบใหม่ที่ยังไม่มีในชุดด่าน

**ผลต่อการทำงาน:** ยังต้องระบุ PbCl2 PbSO4 MgCO3 Fe(OH)2 ใน `docs/chemistry-review.md` ให้อาจารย์เห็นและตัดสินอีกชั้น

## D-16 · ไม่พิมพ์สำรับการ์ดใหม่

**ผลต่อการทำงาน:** `docs/assumptions.md` ต้องมีตารางเทียบว่าไอออนใดมีเฉพาะในการ์ด ไอออนใดมีเฉพาะในเว็บ พร้อมเหตุผล เพื่อให้เขียนลงเล่มได้เลย

## D-21 · `instanceId` ต้องคำนวณจากข้อมูลด่าน ห้ามสุ่ม

**เลือก:** `instanceId` ของการ์ดไอออนทุกใบต้องเป็นค่าที่**คำนวณซ้ำได้เสมอ**จาก `levelId` เช่น
`reactant:silver-plus__nitrate:nitrate:0` ห้ามใช้ `crypto.randomUUID()` หรือเลขลำดับตอน render

**เหตุผล:** Phase 3 เก็บ checkpoint กลางด่านเป็น `slotAssignments: [{slotId, ionInstanceId}]` และ
`canceledPairs: {leftInstanceId, rightInstanceId}` ลง localStorage ถ้า id ถูกสร้างแบบสุ่ม ลำดับจะพังแบบนี้

```
เล่นถึงกลางด่าน -> เซฟว่า "ช่อง 2 มีการ์ด id=abc123"
ปิดแท็บ เปิดใหม่ -> สร้างการ์ดใหม่ ได้ id=xyz789
กู้ checkpoint    -> หา abc123 ไม่เจอ -> ช่องว่างเปล่า หรือแอปพัง
```

ทั้ง spec และแผนเดิมบอกแค่ว่า instanceId ต้อง "unique ภายในสมการ" ไม่ได้บอกว่าสร้างอย่างไร
ช่องโหว่นี้จะไปโผล่ตอน Phase 7 ต่อหน้าจอจริงซึ่งไล่หาสาเหตุยากมาก จึงตัดสินไว้ก่อนเขียน schema

**ผลต่อการทำงาน:**
- Phase 3 ใช้ schema เดิมได้ ไม่ต้องแก้ เพราะ id เป็นสตริงเหมือนเดิม
- Phase 4/6 ที่สร้าง instance ต้องใช้ฟังก์ชัน pure ที่รับ `BuiltLevel` แล้วคืนรายการ instance เดิมทุกครั้ง
- ต้องมีเทสต์ว่า สร้าง instance ของด่านเดียวกันสองครั้งแล้วได้ id ชุดเดียวกันเป๊ะ
- ได้ผลพลอยได้คือ id อ่านออก ทำให้ดีบักและอ่าน checkpoint ในเครื่องนักเรียนได้ง่ายขึ้น
