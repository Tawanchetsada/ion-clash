## ขั้นตอนการทำงาน

### ขั้นที่ 1 · Deploy production

- [ ] เชื่อม Vercel เข้ากับ repo แล้ว deploy จาก `main` ขึ้น production
- [ ] ตั้ง `NEXT_PUBLIC_RESEARCH_ENDPOINT` ใน **Vercel dashboard เท่านั้น** ห้ามอยู่ในซอร์สหรือใน `.env` ที่ถูก commit
- [ ] ตรวจว่า production build ใช้ endpoint ถูกตัว — เล่นจบ 1 ด่านบน production แล้วดู Google Sheet
- [ ] ทดสอบ URL **production** บน iPad จริงอีกรอบ ไม่ใช่แค่ preview
- [ ] ตั้ง Content Security Policy ใน `next.config.ts` — อย่างน้อย `default-src 'self'` และ `connect-src` ที่อนุญาตเฉพาะ endpoint ของ Apps Script
- [ ] ยืนยันว่า `/dev/components` และ `/dev/interaction` **404 จริงบน production** (เปิด URL ตรง ๆ ดูด้วยตา)
- [ ] ยืนยันว่า `/research` เข้าได้ด้วยการพิมพ์ URL แต่ไม่มีลิงก์จากเมนู
- [ ] เปิดครั้งแรกแล้วโหลดเสร็จ และเล่นต่อได้แม้เน็ตหลุดกลางทาง

> **กับดัก:** preview deployment ใช้ environment variable คนละชุดกับ production
> ทดสอบบน preview อย่างเดียวแล้วอาจได้ production ที่ไม่ส่งข้อมูลวิจัยเลยโดยไม่มีใครรู้จนวันทดลอง

### ขั้นที่ 2 · README (AC-15)

`README.md` ที่ราก repo — ต้องตอบให้ครบ

| หัวข้อ | เนื้อหา |
|---|---|
| โปรเจกต์นี้คืออะไร | สรุปสั้น พร้อมลิงก์ production และ repo |
| ติดตั้งและรัน | `npm ci` แล้ว `npm run dev` · ระบุ Node 18.18+ หรือ 20+ |
| คำสั่งทั้งหมด | dev · build · start · lint · typecheck · test · test:e2e · gen:review · gen:audio |
| รันเทสต์ไฟล์เดียว | `npx vitest run <path>` และ `npx vitest run -t "<ชื่อ>"` |
| **วิธีแก้ข้อมูลด่าน** | แก้ที่ `src/data/levelSeeds.ts` เท่านั้น (4 ฟิลด์) แล้วรัน `npm test` และ `npm run gen:review` |
| **วิธีเพิ่มไอออนใหม่** | เพิ่มใน `ions.ts` แล้วเพิ่ม/แก้กฎใน `solubility.ts` — ลำดับกฎเป็นสาระ |
| โครงสร้างโฟลเดอร์ | อธิบายชั้น domain / data / presentation / components / session / storage / research / audio |
| ระบบวิจัย | ลิงก์ไป `docs/research-setup.md` |
| deploy | เชื่อม Vercel กับ repo แล้ว push · ตัวแปรสภาพแวดล้อมที่ต้องตั้ง |
| ข้อควรระวัง | พิธี lockfile หลังแตะ dependency |

### ขั้นที่ 3 · เอกสารส่งมอบ

- [ ] `docs/chemistry-review.md` ที่อาจารย์เซ็นรับรองแล้ว ครบ 50 ด่าน (A-01)
      → รันซ้ำด้วย `npm run gen:review` ก่อนส่ง เพื่อให้ตรงกับข้อมูลล่าสุด **ห้ามแก้ไฟล์นี้ด้วยมือ**
- [ ] `docs/research-setup.md` คู่มือติดตั้ง Google Apps Script ทีละขั้น
- [ ] `docs/assumptions.md` รายการสมมติฐานที่ตั้งไว้ระหว่างพัฒนา
- [ ] `docs/not-done.md` รายการสิ่งที่ยังไม่ได้ทำ — **ต้องไม่มีข้อใดเป็น MUST**
- [ ] `docs/pilot-runbook.md` คู่มือวันทดลอง (ขั้นที่ 4)
- [ ] `CLAUDE.md` ตรงกับโค้ดจริงทุกบรรทัด — ไล่อ่านทั้งไฟล์ ไม่ใช่แก้เฉพาะย่อหน้าสถานะ

**สิ่งที่ต้องมีใน `docs/assumptions.md` อย่างน้อย**

- ตัด O²⁻ · MnO₄²⁻ · CN⁻ ออกจากสำรับการ์ดเดิม พร้อมเหตุผล (D-02)
- เพิ่ม Pb²⁺ · Ba²⁺ · I⁻ · Br⁻ · S²⁻ ที่ไม่มีในสำรับการ์ด
- ตีความ "ไอออน 4 → 4" เป็นการจับคู่ใหม่โดยใช้สัมประสิทธิ์บอกจำนวน (D-03)
- สารที่ละลายน้อยซึ่งจัดเป็นตะกอน: PbCl₂ · PbSO₄ · MgCO₃ · FeS · CuS (D-15)
- เว็บกับสำรับการ์ดกายภาพไม่ตรงกัน 100% และจะไม่พิมพ์ใหม่ (D-16)
- เก็บชื่อผู้เล่นและส่งข้อมูลออกเครือข่าย ซึ่ง**ต่างจาก spec เดิม** (D-14, D-06)
- แผงกฎการละลายระหว่างเล่นที่ไม่หักคะแนน — เพิ่มจาก spec (Phase 8)
- เสียงเป็น `.wav` ไม่ใช่ `.mp3` เพราะไม่มี encoder และ Safari เล่น ogg/webm ไม่ได้ (Phase 5)

### ขั้นที่ 4 · คู่มือวันทดลอง `docs/pilot-runbook.md`

เอกสารหน้าเดียวสำหรับผู้วิจัยใช้จริงหน้างาน — เขียนให้คนที่ไม่ได้เขียนโค้ดอ่านแล้วทำตามได้

**เตรียมก่อนวัน**

- [ ] ทดสอบ Apps Script ยิงข้อมูลเข้า Sheet ได้จริง **อย่างน้อย 1 สัปดาห์ก่อน**
- [ ] เตรียม iPad หรือเครื่องให้ครบ 8 เครื่อง เปิด URL ค้างไว้
- [ ] เคลียร์ localStorage ของทุกเครื่องก่อนเริ่ม
- [ ] พิมพ์บัตรรหัสผู้เรียน S01 ถึง S08
- [ ] เตรียมแบบทดสอบหลังเรียนแบบกระดาษ
- [ ] เตรียมลิงก์ Google Form แบบประเมินความพึงพอใจ (D-08 — ไม่ทำในเว็บ)
- [ ] **ซ้อมเต็มรูปแบบ 1 รอบ** ด้วยเครื่องจริงและบัญชีจริง

**วันทดลอง**

1. แจกบัตรรหัส ให้นักเรียนกรอกรหัสในเว็บ
2. อธิบายและขอความยินยอมการเก็บข้อมูล
3. ให้เล่นตามเวลาที่กำหนด
4. **ก่อนเลิก ให้ทุกคนกดปุ่มคัดลอกผลการเรียนแล้ววางลง Google Form** — ข้อนี้สำคัญที่สุด อย่าให้ใครลืม
5. ทำแบบทดสอบหลังเรียนบนกระดาษ
6. ทำแบบประเมินความพึงพอใจใน Google Form

**หลังทดลอง**

1. ตรวจว่า Google Sheet มีข้อมูลครบ 8 คน
2. ถ้าขาด ให้ใช้ข้อมูลจาก Google Form ที่นักเรียนวางไว้แทน
3. เปิด `/research` นำเข้าข้อมูล กรอกคะแนน E2 จากกระดาษ
4. ส่งออก CSV สำหรับใส่ในเล่มวิทยานิพนธ์

> ข้อ 4 ของวันทดลองคือจุดที่พลาดง่ายที่สุดและกู้คืนยากที่สุด — ควรมีคนคอยไล่เช็กทีละเครื่อง

## กับดักที่ต้องระวัง

| กับดัก | ผลที่ตามมา |
|---|---|
| ทดสอบแค่ preview deployment | production ใช้ environment variable คนละตัว อาจไม่ส่งข้อมูลวิจัยเลย |
| ไม่ซ้อมก่อนวันจริง | เจอปัญหาหน้างานแล้วแก้ไม่ทัน เสียโอกาสเก็บข้อมูลจากนิสิต 8 คน |
| ลืมเคลียร์ localStorage ก่อนเริ่ม | ข้อมูลรอบทดสอบปนกับข้อมูลจริง แยกไม่ออกภายหลัง |
| ไม่ไล่เช็กว่านักเรียนกดคัดลอกครบทุกคน | ข้อมูลบางคนหาย กู้ไม่ได้ |
| อัปเดต `CLAUDE.md` ไม่ทัน | คนที่มาทำต่อได้ข้อมูลผิดตั้งแต่บรรทัดแรก |
| แก้ `docs/chemistry-review.md` ด้วยมือ | ไฟล์นี้ generate อัตโนมัติ — แก้มือแล้วจะขัดกับข้อมูลจริง และลายเซ็นจะรับรองของที่ไม่ตรงกับโค้ด |
| ปล่อยให้ `/dev/*` เปิดได้บน production | นักเรียนกดเข้าไปเจอหน้าเครื่องมือนักพัฒนากลางการทดลอง |
| ลืมตั้ง CSP | เว็บสาธารณะที่ใช้กับผู้เยาว์โดยไม่มี header ความปลอดภัยพื้นฐาน |

## พิธีปิดโปรเจกต์

1. ทุกช่องในขั้นที่ 5 ติ๊กครบ
2. เขียนบล็อกสถานะต้นไฟล์นี้ — สรุปว่า deploy วันไหน URL อะไร ซ้อมวันไหน ผลเป็นยังไง
3. อัปเดต `development-plan/README.md` ให้ทุกแถวเป็น ✅ และติ๊ก Definition of Done ทั้ง 7 ข้อ
4. อัปเดต `CLAUDE.md` ครั้งสุดท้ายให้ตรงกับโค้ดที่ส่งมอบจริง
5. commit + push · รอ CI เขียว · ติด git tag เช่น `v1.0-pilot` ที่ commit ที่ใช้ในวันทดลองจริง

> **ติด tag สำคัญกว่าที่คิด** — เล่มวิทยานิพนธ์ต้องอ้างอิงได้ว่าข้อมูลชุดนี้เก็บจากโค้ดเวอร์ชันไหน
> ถ้าแก้โค้ดต่อหลังการทดลองแล้วไม่มี tag จะย้อนกลับไปบอกไม่ได้ว่านักเรียนเล่นเวอร์ชันอะไร
